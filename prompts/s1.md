# S1 prompts: AGENTS.md, Brainstorm, Spec, Plan

Tested with opencode 1.19.5, model `ninerouter/sol`, clean config (no extra skills). Final result: **3 of 3 runs passed all five acceptance checks with identical prompts**, each from an empty folder, with the final prompt set below (re-run after review; the first round of runs is superseded). Reference repo: `financial-app/` (copy of run 2), tags `s1-start` and `s1-spec`.

How the prompts were run: `opencode run` for the first message and `opencode run -c` for each reply. In the course, participants type the same text into the opencode window (the TUI). Test runs pushed to a local bare repo. **Real participants push to GitHub.**

Two things apply to every step, so read them first.

**1. The agent can stall.** In about 1 in 7 `/init` test runs (3 of 20, with or without `--auto`) the agent stopped after its first step and sat there until the 10-minute timeout. A retry of the same prompt worked each time. Tell participants: if nothing moves for 2 minutes, press `Esc` and send the same prompt again.

**2. The agent sometimes mistypes a file name.** It occasionally reads a path with stray characters on the end (`AGENTS.md battle`, `docs/spec.md ma`, a leading space). The screen then shows `Error: File not found` and, usually, "Did you mean…?". The agent corrects itself in the next step. This happened in runs 1 and 3 of the final set. It does no harm; it is noise participants may see.

## 1. Init + one rule

**Prompt 1.** Type `/init` in the opencode window and press Enter.

(In the test runs this was `opencode run --auto --command init`. `opencode run "/init"` also works, but see the permission problem below.)

**Prompt 2:**

```text
Add one rule to AGENTS.md: Explain what you will do in plain business language before doing it.
```

(17 words.)

**Good result:** `AGENTS.md` exists after `/init`, with 2–4 short generic bullets ("repo is empty, no build commands yet"). After prompt 2 the rule is in the file word for word. No other files are created. Then `git add -A`, commit, push (`s1-start`).

**Variation (3 final runs):**
- `/init` took 43–55 s. Prompt 2 changed the file within seconds.
- `/init` wrote an empty-project note of 2–4 bullets, worded differently each time.
- Rule placement: run 1 added it as the **last** bullet; run 2 as the **first** bullet; run 3 as the **first** bullet, with a blank line after it. All three contain it verbatim.

### Problem: `/init` was rejected with a permission error (and what participants will see)

**What happened.** In the first round, run 2's `/init` ended with:

```
! permission requested: external_directory (/var/tmp/day3-runs/*); auto-rejecting
Error: The user rejected permission to use this specific tool call.
```

and no `AGENTS.md` was created (the rule prompt created the file instead). My earlier report wrongly said `/init` made the file in all three runs.

**Cause.** While looking around the project, the agent tried to read a path just *outside* the project folder. The log shows `/var/tmp/day3-runs/s1-run2?`, a sibling path with a stray character on the end. Both rejected runs (`s1-run2?` and another with `t7cat`) show the same file-name glitch as the one described at the top. Anything outside the project folder triggers opencode's "external directory" permission. `opencode run` has no one to ask, so it auto-rejects. The agent then stops or carries on without the file. I found it by reading the JSON event logs of 12 plain `opencode run --command init` runs: 1 hit this rejection, 1 stalled, 10 were fine. With `--auto` (auto-approve): 8 runs, 0 rejections, 2 stalls.

**What participants will see in the opencode window (TUI).** I reproduced the dialog in the real TUI by asking the agent to look at the parent folder (the dialog text below is copied from that screen). A box appears above the input line:

```
△ Permission required
  ← Access external directory /var/tmp/day3-runs
  Patterns:  - /var/tmp/day3-runs/*
  [ Allow once ]  [ Allow always ]  [ Reject ]      ⇆ select   enter confirm
```

The agent waits until you choose. **Tell participants to choose "Allow once"** (it is the highlighted default, so Enter is enough). I pressed Enter on it and the agent finished (builder-reported; no screenshot of the dialog was kept). I did not test Reject in the TUI. By the CLI result, it should give the agent the same "user rejected" error, so `/init` may end without a file; the fix is to send `/init` again. I also ran plain `/init` once in the TUI (empty folder): `AGENTS.md` was written and I saw no dialog. So the dialog is occasional, not guaranteed. I did not test "Allow always".

**Reliable way for the reference runs.** The test runs used `opencode run --auto --command init` (auto-approve). The 3 final runs created `AGENTS.md`. Of 8 earlier `--auto` runs, 6 did and 2 stalled (no rejections). `--auto` is a command-line flag. It is **not** how participants run it, so do not put it on a slide. For participants the answer is the TUI dialog above.

**Prompt change.** None. A prompt that avoids the external access is not possible, because the agent decides which paths to read. Participants either click "Allow once" or re-send.

## 2. Brainstorm

**Prompt:**

```text
Let's brainstorm a NISP stock dashboard together. It should show the latest price, the daily change and a 1-year price chart. Ask me one question at a time, at most 5, in plain business language. Don't write any code or files yet.
```

(42 words.) The stack is not in this prompt, so the brainstorm stays about the business. It goes in the spec prompt.

**Good result:** The agent asks one short business question per turn, about 5 s each. No files are created. After the 5th answer it replies with a 3-bullet summary of what was agreed. In all 3 runs: 5 questions, then the summary.

**Questions asked and answers given.** Answers are written to fit whatever the agent asked.

| # | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| 1 | Who will use this and what decision should it help with? → "Our sales team. They want to see how NISP is doing before client meetings." | same (wording differs slightly) → same answer | Individual investors, advisers, or an internal team? → same answer |
| 2 | Live, delayed or end of day? → "Delayed is fine, as long as it shows when it was updated." | same → same | Live, or delayed with a last-updated time? → same |
| 3 | Daily change in both amount and percentage? → "Yes, both amount and percentage." | Rupiah, percentage, or both? → "Both amount and percentage." | NISP alone, or compare to a benchmark? → "Just NISP, a simple price trend." |
| 4 | Simple trend or select a date? → "A simple trend is enough." | Laptops, phones, or both? → "Mostly laptops." | Laptops or phones? → "Mostly laptops." |
| 5 | Laptops, phones, or both? → "Mostly laptops." | Hover over a date, or simple trend line? → "A simple trend line is enough." | Shared internal link, or sign-in? → "A shared link is fine, no sign-in." |
| 6 | Summary (laptops, delayed price in rupiah with timestamp, amount and percentage, simple trend, no date selection) | Summary (same facts, "without hover details") | Summary (laptops, shared link with no sign-in, delay notice, no benchmark) |

**Variation:**
- The first question was about the audience in all runs (runs 1 and 2 also asked what decision it supports; run 3 asked only who uses it). After that the order and topics differed. Every run covered freshness and device; runs 1 and 2 asked about the daily-change format and chart interaction, run 3 asked about benchmark and sign-in.
- Never more than 5 questions, never more than one per turn, no files created in any run.
- Tip: answer exactly what was asked, in one short sentence.

**Problems and prompt changes:** none in the final set. In the first round, the version "Brainstorm a NISP stock dashboard with me … Don't write any code or files yet" also worked. I kept the "Let's brainstorm … together" wording because it reads more naturally.

## 3. Spec

**Prompt:**

```text
Write what we agreed to docs/spec.md. Use three sections: Goals, Out of scope, and How we'll know it works. Don't build anything yet. We'll use React + Vite, FastAPI (Python) and yfinance, with endpoints GET /api/quote/{ticker} and GET /api/history/{ticker}?period=1y, server on port 8000, page on port 5173.
```

(47 words.) The stack is stated here, in one plain sentence, so participants don't need to know it.

**Good result:** `docs/spec.md` with three headings: Goals, Out of scope, How we'll know it works, about 280–340 words. Goals names React + Vite on 5173, FastAPI on 8000, yfinance and both endpoints. Out of scope lists what the user said no to (live prices, benchmark, hover, sign-in, phone-first). The "know it works" section describes what the user will see. Takes 24–33 s. Participants read it and correct anything wrong.

**Variation:**
- All three specs have the three sections and name every stack item, both endpoints and both ports (checked by script).
- Out of scope followed each run's own answers: run 1 "no date selection", run 2 "no hover", run 3 "no benchmark" and "no sign-in". All three list "building the app at this stage" as out of scope, which is harmless.

**Problems and prompt changes:**
- The first draft was: "Write what we agreed to docs/spec.md with three sections … Build it with React + Vite for the page …". The word **"Build it"** made the agent build the whole app (`frontend/`, `backend/`, tests; 8 minutes). The fix was "Don't build anything yet. We'll use …". With it, 6 of 6 runs (3 in each round) wrote only the spec.
- Never reply "Yes, go ahead" after the brainstorm summary; that also invites a build. Always use the spec prompt.

## 4. Plan (Plan mode), review, then save

### 4a. Ask for the plan

Switch to **Plan mode** first (press `Tab` in the opencode window; the footer then says "plan"). Test runs used `--agent plan`.

```text
Read docs/spec.md and give me a numbered step-by-step plan to build it. Don't build anything yet.
```

(16 words.)

**Good result:** A numbered list of 8 steps, each with a bold title and 1–2 lines. The steps follow the spec in order: set up, data contract, yfinance, the two endpoints, the laptop page and chart, loading and error states, verify. It takes 17–23 s and changes no files.

### 4b. Read the plan, then approve, edit or reject (the checkpoint)

Participants read the plan on screen and decide:

- **Approve:** go straight to 4c.
- **Edit:** ask for a change in plain words and read the new plan. Tested prompt (same Plan-mode session):

```text
Add one more step at the end: write a short README that explains how to start the app. Show me the updated plan.
```

(23 words.) Replayed in all 3 runs: the agent returned the full list with a ninth step "Write a short README" (10–12 s), changed no files, and left steps 1–8 as they were. The same pattern works for "Change step 5 to …" (not run).
- **Reject:** say what is wrong ("This plan builds more than the spec asks for. Make it shorter.") or start over with 4a. Reject was not run; it is the same loop as Edit.

Check against the spec before approving. The runs showed things worth checking. Run 3's plan added "short-lived caching" and "prepare shared access" (hosting, usage terms), which are not in the spec. A participant could reject or edit those.

### 4c. Save the approved plan

Switch back to **Build mode** (`Tab` again; the footer says "build") and stay in the same conversation:

```text
Save that plan to docs/plan.md. Don't build anything yet.
```

(9 words.) Plan mode cannot write files, so saving needs Build mode. Because it is the same session, the agent saves the plan it just showed, including the README step. This worked 3 of 3 times (18–19 s). Then `git add -A`, commit, push (`s1-spec`).

**Good result:** `docs/plan.md` exists with numbered steps (9 after the README edit). Still no `frontend/` or `backend/`.

**Variation:**
- Plans had 8 steps before the edit and 9 after, in every run. Wording and order differ: run 2 starts with the data contract, runs 1 and 3 with project set-up.
- All plans use the correct ports and endpoints. `docs/plan.md` had the same steps as the last plan shown (runs 1 and 2 added a "Build plan" heading).
- The reference repo `financial-app/` is run 2 and contains the 9-step plan. Its AGENTS.md has the rule as the first bullet.

**Problems and prompt changes:**
- **Retry needed in the first round.** In the first round's run 1 the plan prompt had to be sent twice (the first reply was a "File not found" error on a mistyped path), so that session has two identical Plan messages. In the final set no resend was needed. Runs 1 and 3 each showed one or two recoverable file-name errors (see the note at the top).
- In the first round, "Don't build anything yet" was kept in both plan prompts because the build agent can start coding after "Save that plan".
