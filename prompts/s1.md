# S1 prompts: AGENTS.md, Brainstorm, Spec, Plan

Re-tested with NISP on 2026-11-12; earlier BBCA runs superseded.

Tested with opencode 1.19.5, model `ninerouter/sol`, clean config (no extra skills). Final result: **3 of 3 runs passed all five acceptance checks with identical prompts** (plus a check that `docs/spec.md` names NISP and never BBCA), each from an empty folder, with the final prompt set below. One prompt changed after the first NISP attempt (brainstorm, see section 2), and the count was restarted. Reference repo: `financial-app/` (copy of run 1), tags `s1-start` and `s1-spec`.

How the prompts were run: `opencode run` for the first message and `opencode run -c` for each reply. In the course, participants type the same text into the opencode window (the TUI). Test runs pushed to a local bare repo. **Real participants push to GitHub.**

Two things apply to every step, so read them first.

**1. The agent can stall.** In about 1 in 7 `/init` test runs (3 of 20, with or without `--auto`) the agent stopped after its first step and sat there until the 10-minute timeout. A retry of the same prompt worked each time. It happened once in the NISP runs too: run 3's spec prompt printed nothing for 600 s, no file was written, and the same prompt sent again worked (35 s). That retry is the only one in the final set. Tell participants: if nothing moves for 2 minutes, press `Esc` and send the same prompt again.

**2. The agent sometimes mistypes a file name.** It occasionally reads a path with stray characters on the end (`AGENTS.md battle`, `docs/spec.md ma`, a leading space). The screen then shows `Error: File not found` and, usually, "Did you mean…?". The agent corrects itself in the next step. This happened in runs 1 and 3 of the NISP set (run 1: during `/init`, the plan read and the save; run 3: during `/init` and the spec read). Run 2 had none. It does no harm; it is noise participants may see.

## 1. Init + one rule

**Prompt 1.** Type `/init` in the opencode window and press Enter.

(In the test runs this was `opencode run --auto --command init`. `opencode run "/init"` also works, but see the permission problem below.)

**Prompt 2:**

```text
Add one rule to AGENTS.md: Explain what you will do in plain business language before doing it.
```

(17 words.)

**Good result:** `AGENTS.md` exists after `/init`, with 2–4 short generic bullets ("repo is empty, no build commands yet"). After prompt 2 the rule is in the file word for word. No other files are created. Then `git add -A`, commit, push (`s1-start`).

**Variation (3 final runs):**
- `/init` took 41–46 s. Prompt 2 took 10–13 s.
- `/init` wrote an empty-project note of 2–4 bullets, worded differently each time.
- Rule placement: all three runs put it as the **first** bullet, under the heading, word for word. Runs 1 and 2 left a blank line after it; run 3 did not.

### Problem: `/init` was rejected with a permission error (and what participants will see)

**What happened.** In the first round, run 2's `/init` ended with:

```
! permission requested: external_directory (/var/tmp/day3-runs/*); auto-rejecting
Error: The user rejected permission to use this specific tool call.
```

and no `AGENTS.md` was created (the rule prompt created the file instead). My earlier report wrongly said `/init` made the file in all three runs.

**Cause.** While looking around the project, the agent tried to read a path just *outside* the project folder. The log shows `/var/tmp/day3-runs/s1-run2?`, a sibling path with a stray character on the end. Both rejected runs (`s1-run2?` and another with `t7cat`) show the same file-name glitch as the one described at the top. Anything outside the project folder triggers opencode's "external directory" permission. `opencode run` has no one to ask, so it auto-rejects. The agent then stops or carries on without the file. I found it by reading the JSON event logs of 12 plain `opencode run --command init` runs: 1 hit this rejection, 1 stalled, 10 were fine. With `--auto` (auto-approve): 8 runs, 0 rejections, 2 stalls.

**What participants will see in the opencode window (TUI).** I reproduced the dialog in the real TUI by asking the agent to look at the parent folder (the dialog text below is copied from that screen). A box appears above the input line:

```
△ Permission required
  ← Access external directory /var/tmp/day3-runs
  Patterns:  - /var/tmp/day3-runs/*
  [ Allow once ]  [ Allow always ]  [ Reject ]      ⇆ select   enter confirm
```

The agent waits until you choose. **Tell participants to choose "Allow once"** (it is the highlighted default, so Enter is enough). I pressed Enter on it and the agent finished (builder-reported; no screenshot of the dialog was kept). I did not test Reject in the TUI. By the CLI result, it should give the agent the same "user rejected" error, so `/init` may end without a file; the fix is to send `/init` again. I also ran plain `/init` once in the TUI (empty folder): `AGENTS.md` was written and I saw no dialog. So the dialog is occasional, not guaranteed. I did not test "Allow always".

**Reliable way for the reference runs.** The test runs used `opencode run --auto --command init` (auto-approve). The 3 NISP runs created `AGENTS.md` with no rejection. Of 8 earlier (BBCA-era) `--auto` runs, 6 did and 2 stalled (no rejections). `--auto` is a command-line flag. It is **not** how participants run it, so do not put it on a slide. For participants the answer is the TUI dialog above.

**Prompt change.** None. A prompt that avoids the external access is not possible, because the agent decides which paths to read. Participants either click "Allow once" or re-send.

## 2. Brainstorm

**Prompt:**

```text
Let's brainstorm a NISP (Bank OCBC NISP, NISP.JK) stock dashboard together. It should show the latest price, the daily change and a 1-year price chart. Ask me one question at a time, at most 5, in plain business language. Don't write any code or files yet.
```

(46 words.) The stack is not in this prompt, so the brainstorm stays about the business. It goes in the spec prompt.

**Good result:** The agent asks one short business question per turn, about 4–7 s each. No files are created. After the 5th answer it replies with a short summary of what was agreed (3–4 bullets). In all 3 runs: 5 questions, then the summary.

**Questions asked and answers given.** Answers are written to fit whatever the agent asked.

| # | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| 1 | Who will use this and what decision should it help with? → "Our sales team. They want to see how NISP is doing before client meetings." | same (wording differs slightly) → same answer | same as run 1 → same answer |
| 2 | Live, or delayed / end of day? → "Delayed is fine, as long as it shows when it was updated." | How fresh: live, 15–20 min delayed, or end of day? → same | How fresh: live, about 15 min delayed, or latest close? → same |
| 3 | Simple price trend, or compare with a benchmark (IHSG)? → "Just NISP, a simple price trend." | Simple trend, or hover over a date? → "A simple trend line is enough." | Daily change in rupiah and percentage? → "Yes, both amount and percentage." |
| 4 | Laptops or phones? → "Mostly laptops." | Laptops, phones, or both? → "Mostly laptops." | Simple trend, or point to a date? → "A simple trend is enough." |
| 5 | Add a short company overview, or only stock performance? → "Keep it strictly to stock performance." | Only NISP, or compare with IHSG? → "Just NISP, no comparison." | Phones or laptops? → "Mostly laptops." |
| 6 | Summary (laptop-first, NISP.JK only, delayed IDR price with timestamp, daily change in IDR and %, simple 1-year chart, no benchmark or overview) | Summary (same facts; "no comparison or hover interaction") | Summary (same facts; also a visible data source and a warning if updates are unavailable) |

**Variation:**
- The first question was about the audience and the decision it supports in all three runs. After that the order and topics differed. Every run covered freshness and device; runs 1 and 2 asked about benchmark / IHSG, runs 2 and 3 about chart interaction, run 1 about a company overview, run 3 about the daily-change format.
- Never more than 5 questions, never more than one per turn, no files created in any run.
- With the fixed prompt, no run asked which company NISP is, and the spec names Bank OCBC NISP and `NISP.JK` in all three runs.
- Tip: answer exactly what was asked, in one short sentence.

**Problems and prompt changes:**
- **Changed in this re-test.** The first NISP attempt used the old wording with only "NISP": "Let's brainstorm a NISP stock dashboard together. …". Run 1 asked about the audience, but runs 2 and 3 both opened with "Which company and stock exchange do you mean by NISP?". That wastes one of the 5 questions and could end with the wrong company or ticker. The attempt was stopped after the first message and the count restarted.
  - Old: `Let's brainstorm a NISP stock dashboard together.`
  - New: `Let's brainstorm a NISP (Bank OCBC NISP, NISP.JK) stock dashboard together.` (4 words added.)
  - With the new prompt, 3 of 3 runs started with the audience question, and none confused NISP with OCBC Singapore.
- An earlier BBCA round showed that "Brainstorm a … stock dashboard with me … Don't write any code or files yet" also worked. I kept the "Let's brainstorm … together" wording because it reads more naturally.

## 3. Spec

**Prompt:**

```text
Write what we agreed to docs/spec.md. Use three sections: Goals, Out of scope, and How we'll know it works. Don't build anything yet. We'll use React + Vite, FastAPI (Python) and yfinance, with endpoints GET /api/quote/{ticker} and GET /api/history/{ticker}?period=1y, server on port 8000, page on port 5173.
```

(47 words.) The stack is stated here, in one plain sentence, so participants don't need to know it.

**Good result:** `docs/spec.md` with three headings: Goals, Out of scope, How we'll know it works, about 300–330 words. Goals names React + Vite on 5173, FastAPI on 8000, yfinance and both endpoints. Out of scope lists what the user said no to (live prices, benchmark, hover or point-to-a-date, company overview, phone-first). The "know it works" section describes what the user will see. Takes about 24 s. The spec says "Bank OCBC NISP" and uses `NISP.JK` as the ticker. Participants read it and correct anything wrong.

**Variation:**
- All three specs (298, 299 and 326 words) have the three sections and name every stack item, both endpoints and both ports (checked by script). Each names NISP / `NISP.JK` and none contains BBCA. None mentions OCBC Singapore.
- Out of scope followed each run's own answers: run 1 "no benchmark" and "no company overview", run 2 "no hover" and "no IHSG", run 3 "no pointing to a date". All three list "building the app at this stage" as out of scope, which is harmless.
- Run 3's first spec attempt stalled (see the note at the top) and was re-sent once.

**Problems and prompt changes:**
- (Found in the earlier BBCA round; not repeated in the NISP runs.) The first draft was: "Write what we agreed to docs/spec.md with three sections … Build it with React + Vite for the page …". The word **"Build it"** made the agent build the whole app (`frontend/`, `backend/`, tests; 8 minutes). The fix was "Don't build anything yet. We'll use …". With it, 6 of 6 earlier runs wrote only the spec, and so did 3 of 3 NISP runs.
- Never reply "Yes, go ahead" after the brainstorm summary; that also invites a build. Always use the spec prompt.

## 4. Plan (Plan mode), review, then save

### 4a. Ask for the plan

Switch to **Plan mode** first (press `Tab` in the opencode window; the footer then says "plan"). Test runs used `--agent plan`.

```text
Read docs/spec.md and give me a numbered step-by-step plan to build it. Don't build anything yet.
```

(16 words.)

**Good result:** A numbered list of 7–8 steps, each with a bold title and 1–2 lines. The steps follow the spec: set up, data contract, yfinance, the two endpoints, the laptop page and chart, loading and error states, verify. It takes 15–19 s and changes no files.

### 4b. Read the plan, then approve, edit or reject (the checkpoint)

Participants read the plan on screen and decide:

- **Approve:** go straight to 4c.
- **Edit:** ask for a change in plain words and read the new plan. Tested prompt (same Plan-mode session):

```text
Add one more step at the end: write a short README that explains how to start the app. Show me the updated plan.
```

(23 words.) Replayed in all 3 runs: the agent returned the full list with a final step "Write a short README" (11 s), changed no files, and left the earlier steps as they were (run 1 reworded a few). The same pattern works for "Change step 5 to …" (not run).
- **Reject:** say what is wrong ("This plan builds more than the spec asks for. Make it shorter.") or start over with 4a. Reject was not run; it is the same loop as Edit.

Check against the spec before approving. The runs showed something worth checking: the plans of run 1 ("briefly cache results") and run 2 ("brief caching") added caching, which is not in the spec. A participant could reject or edit that.

### 4c. Save the approved plan

Switch back to **Build mode** (`Tab` again; the footer says "build") and stay in the same conversation:

```text
Save that plan to docs/plan.md. Don't build anything yet.
```

(9 words.) Plan mode cannot write files, so saving needs Build mode. Because it is the same session, the agent saves the plan it just showed, including the README step. This worked 3 of 3 times (17–23 s). Then `git add -A`, commit, push (`s1-spec`).

**Good result:** `docs/plan.md` exists with numbered steps (8–9 after the README edit). Still no `frontend/` or `backend/`.

**Variation:**
- Plans had 8 steps (runs 1 and 3) or 7 steps (run 2) before the edit, and 9, 8 and 9 after. Wording and order differ: run 2 starts with the data contract, runs 1 and 3 with project set-up.
- All plans use the correct ports and endpoints and name `NISP.JK`. `docs/plan.md` had the same steps as the last plan shown, with no heading.
- The reference repo `financial-app/` is run 1 and contains the 9-step plan. Its AGENTS.md has the rule as the first bullet.

**Problems and prompt changes:**
- **No resend needed in the plan steps.** Run 1 showed recoverable file-name errors on the plan read and the save (the agent corrected itself both times). The only resend in the whole set was run 3's stalled spec prompt.
- "Don't build anything yet" was kept in both plan prompts because the build agent can start coding after "Save that plan".
