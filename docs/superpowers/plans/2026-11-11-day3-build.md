# Day 3 Build Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship Day 3: three tested HTML decks, a reference Financial App with 10 checkpoints, three handouts and a facilitator guide.

**Architecture:** We build the reference app first, by driving opencode with the same prompts participants will use, so every hands-on slide quotes a prompt that has already worked. Deck copy is written from those tested prompts, then built into HTML. Each task goes to a fresh builder subagent, and a reviewer on a different model family checks it against the spec before the next task starts.

**Tech Stack:** opencode (participant harness) · React + Vite · FastAPI · SQLite · yfinance · OpenAI-compatible LLM API · single-file HTML decks (`frontend-slides`) · `python-pptx` or equivalent for S3 output.

**Spec:** `docs/superpowers/specs/2026-11-11-day3-design.md` · **Outline:** `docs/outlines/day3-outline.md` · **Log:** `docs/project-log.md`

## Global Constraints

- Every prompt shown on a slide or in a handout has worked **3 times in a row from a clean start** in opencode **with no extra skills installed**.
- The app stack is named in the prompts: React + Vite frontend, FastAPI backend, SQLite, yfinance (`BBCA.JK`, `BBRI.JK`, `TLKM.JK`).
- LLM config lives in `backend/.env` as `LLM_BASE_URL`, `LLM_API_KEY` and `LLM_MODEL`. Only `.env.example` is committed.
- Every checkpoint ships `backend/data/cache/`, so the app runs with Yahoo unreachable.
- The chatbot never recommends buying or selling, cites its data or Wiki page, and says when it doesn't know.
- Decks follow `AGENTS.md`: English; assertion titles; ≤40 visible words per slide or reveal step; ≤60 on hands-on and instruction slides; exceptions are prompts, code, quiz choices and reference tables, each with a one-line reason; speaker notes.
- Each session's blocks add up to exactly 180 minutes (spec §7).
- No invented numbers or regulatory claims. Placeholders, such as model names, are listed in the final report.

## Fixed app interface

The prompts pin this API so that checkpoints, smoke tests and Day 4 all agree:

| Method | Path | Added at | Returns |
|--------|------|----------|---------|
| GET | `/api/quote/{ticker}` | s1-dashboard | `{ticker, price, change, change_pct, as_of}` |
| GET | `/api/history/{ticker}?period=1y` | s1-dashboard | `[{date, close}]` |
| POST | `/api/chat` body `{messages:[{role,content}]}` | s1-chatbot | `{reply}` |
| GET | `/api/watchlist` | s2-watchlist | `[{ticker, name, price, change_pct}]` |
| POST | `/api/watchlist` body `{ticker}` | s2-watchlist | `{ticker}` |
| DELETE | `/api/watchlist/{ticker}` | s2-watchlist | `204` |
| POST | `/api/refresh` | s2-database | `{rows_added}` |

Backend runs on port 8000 and frontend on 5173.

## Review Focus

1. **Yahoo is unreachable or rate-limited** → the app serves cached data and shows "cached as of <date>". Test: smoke run with `YF_OFFLINE=1`.
2. **Wrong or unknown ticker typed into the watchlist** (`BBCA` without `.JK`, `XXXX.JK`) → a clear message, and nothing saved. Test is in Task 3.
3. **Windows path and shell differences** (PowerShell, `py` vs `python`, `.venv\Scripts\activate`) → handouts give both forms. Check is in Task 9.
4. **The chatbot is asked "should I buy BBCA?"** → it declines and gives facts and risks. Test is in Tasks 2 and 4.
5. **A participant switches checkpoints mid-session** → their `.env` survives and the app starts with one command. Test is in Task 2 (recovery sentence).

## Roles

| Role | Model | Notes |
|------|-------|-------|
| Coordinator | this session | dispatches, updates the log, talks to the user |
| Builder | `fedora/sonnet` | fresh worker per task |
| Reviewer | a different family from the builder, picked at dispatch (checked with `pi --list-models`) | read-only; passes or returns findings; loop until it passes |
| Final reviewer | the strongest available model, a different family from the builder | Task 10 |

### Task 1: S1 reference build — `s1-start`, `s1-spec`

**Files:** `financial-app/AGENTS.md`, `financial-app/docs/spec.md`, `financial-app/docs/plan.md`, `prompts/s1.md` (in vibe-training: tested prompts, with expected results and run notes)

- [ ] In an empty folder, run opencode `/init` and add the rule "Explain what you will do in plain business language before doing it." Tag `s1-start`.
- [ ] Draft the brainstorm prompt. It must make the agent ask one question at a time, at most 5 questions, about a BBCA dashboard (price, change, 1-year chart). Run it, answering as a business user.
- [ ] Prompt for the spec → `docs/spec.md` with Goals, Out of scope and How we'll know it works.
- [ ] Switch to Plan mode, then prompt for `docs/plan.md` with numbered steps that name the stack and the fixed interface. Tag `s1-spec`.
- [ ] Repeat the whole sequence 3 times from clean. Record each prompt verbatim in `prompts/s1.md`, with what a good result looks like and the variations seen.
- [ ] Review gate: the reviewer checks that the spec has all three sections and the plan names the stack and endpoints.

### Task 2: S1 reference build — `s1-dashboard`, `s1-chatbot`

**Files:** `financial-app/frontend/**`, `financial-app/backend/main.py`, `backend/.env.example`, `backend/data/cache/`, `financial-app/tests/smoke.py`, `prompts/s1.md`

**Produces:** the `/api/quote`, `/api/history` and `/api/chat` endpoints above; the cache layout `backend/data/cache/<ticker>-<period>.json`.

- [ ] Write `tests/smoke.py` (coordinator, not opencode). Pass `--checkpoint s1-dashboard` or `--checkpoint s1-chatbot`. Asserts:
  - quote: `price > 0`
  - history: ≥200 rows
  - with `YF_OFFLINE=1`: the same calls still succeed
  - chat: posting `[{user:"What is BBCA's latest price?"}]` gives a reply containing the quote price rounded to the nearest whole rupiah
  - chat follow-up: sending that whole history plus "And one month ago?" gives a reply containing a number from history
  - chat: "Should I buy BBCA?" gives a reply that contains no "buy"/"sell" recommendation (the reviewer judges this by reading)
- [ ] Run the smoke test on the empty app. Expected: FAIL (connection refused).
- [ ] Execute the approved plan through opencode with a prompt like "Approve the plan, build the dashboard." Open the app in a browser.
- [ ] Run the smoke test at `s1-dashboard`. Expected: PASS. Tag `s1-dashboard`.
- [ ] Chatbot prompt: update the spec, get a new plan, approve, build. The frontend must send the full message list. Run the smoke test at `s1-chatbot`. Expected: PASS. Tag.
- [ ] Debug drill: break something on purpose (wrong `.env` key) and record the "paste the error and ask the agent to explain it" prompt and its result.
- [ ] Recovery test: from a different checkpoint, run the recovery sentence. Expected: `.env` is kept and the smoke test passes.
- [ ] Repeat 3× clean. Update `prompts/s1.md`. Review gate.

- [ ] Extend the smoke test with `--checkpoint s2-watchlist`: add `TLKM.JK` → it appears in `GET /api/watchlist`; delete it → it's gone; add `BBCA` → a 4xx with a message suggesting `BBCA.JK`; add `XXXX.JK` → a 4xx.
- [ ] Run the extended tests. Expected: FAIL.
- [ ] Through opencode: brainstorm the watchlist → update the spec → approve the plan → build. Tag `s2-database` and `s2-watchlist` when their tests pass.
- [ ] Record the "show me what's inside the database" prompt and its output; it becomes a slide.
- [ ] Repeat 3× clean. Review gate.

### Task 4: S2 reference build — `s2-wiki`

**Files:** `financial-app/wiki/*.md`, `backend/` system prompt, `prompts/s2.md`, `prompts/s2-baseline.md` (the 3 questions, with before and after answers)

- [ ] Pick 3 baseline questions that an OJK investor-education source answers, for example: what OJK supervises, what a stock's ARB limit is, what to check before investing. Record the chatbot's answers **before** the Wiki is added.
- [ ] Through opencode: add the Wiki to the spec → plan → "search the web for official OJK/IDX investor-education material" → pages with source URLs → connect to the chatbot, with a system prompt (role; cite sources; no buy/sell advice; say when unknown).
- [ ] Reviewer verifies: every Wiki page's source URL is on `ojk.go.id`, `idx.co.id` or `ksei.co.id`, and the URL resolves; every claim on a page appears in its source.
- [ ] Re-ask the 3 questions and record the answers after. Expected: the answers cite Wiki pages. Tag `s2-wiki` (the vetted Wiki ships here).
- [ ] Repeat 3× clean (web search results will vary; record the spread). Review gate.

### Task 5: S3 reference build — `s3-report`, `s3-pptx`, `s3-workflow`

### Task 7: Deck style (coordinator + user gate)

- [ ] Use `frontend-slides` to make 3 style previews, each rendering a talk, a hands-on and a check slide from the S1 copy.

### Task 8: Build decks, one task per session (3 parallel workers)

**Files:** `decks/day3-s1.html`, `decks/day3-s2.html`, `decks/day3-s3.html`

- [ ] Skill: `frontend-slides`, "Low density / speaker-led", in the chosen style. It may not add slides, bullets or claims.
- [ ] Hands-on slide component: goal, prompt in a copy box with a working copy button, "you should see", a time-box, and a "stuck?" line pointing to a checkpoint.
- [ ] Check slide component: the question, choices revealed on click, then the answer.
- [ ] Speaker notes present on every slide.
- [ ] Verify in a headless browser: every slide renders at 1280×720 and 1920×1080 with no overflow; the copy buttons copy the exact prompt; screenshots go to `.scratch/decks/`.
- [ ] Review gate: the reviewer looks at the screenshots against the copy file.

### Task 9: Handouts and facilitator guide

**Files:** `handouts/day3-s{1,2,3}.md` and `.html`; `facilitator/day3-guide.md`

- [ ] Handouts: one page per hands-on block, with the prompt, the expected result, a check, and what to do if stuck (the checkpoint plus the recovery sentence). Give Windows and macOS forms wherever commands differ.
- [ ] Guide: pre-session checklist (API key works, Yahoo reachable, GitHub signup works), timing sheet from spec §7, the failures seen in Tasks 1–5 with their fixes, and the checkpoint URLs.
- [ ] Review gate: the reviewer checks that the handout prompts are identical to the deck and to `prompts/`.

### Task 10: Final check

- [ ] Dry run: one clean pass through all of Day 3 from `s1-start`, using only the handouts, timed per block.
- [ ] Final reviewer: the whole deliverable set against the spec §11 "Done means".
- [ ] Report to the user: each slide's title, word count and any exception; the placeholders; the *(verify)* items still open.
