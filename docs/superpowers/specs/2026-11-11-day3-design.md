## 1. Intent

Day 3 of "AI Vibe Coding for Business Users" (Days 3–5, 9 sessions). Business users with no programming background learn to direct an AI coding agent, **opencode**, to build a real app: a Financial App for Indonesian stocks, with NISP as the running example.

Concept: *use case first, technology later.* We teach people to turn a business need into instructions for an AI, judge the result, test it and iterate. We don't teach programming.

Day 3 must leave **every** participant with a working app. Days 4–5 extend the same app with an exposed API, MCP, scraping, login and RBAC, admin and audit, Docker/VPS and monitoring.

## 2. Audience and setting

- Business users. No coding background is assumed.
- Laptops are mixed Windows and macOS. **opencode, model access, Python and Node.js are preinstalled** *(user)*.
- The class has an **OpenAI-compatible LLM API** (base URL, key, model). The in-app chatbot uses it *(user)*.
- GitHub accounts are **created during S1** *(user)*.
- Each session is **3 hours**, interactive, with Q&A and hands-on work *(user)*.
- Decks are **English** HTML *(user)*. Speaking during the session may be Bahasa Indonesia.

## 3. Learning objectives

By the end of each session a participant can:

**S1**
1. Explain that the model doesn't remember; the agent sends the context it needs every turn.
2. Explain what the context window is, and what happens when it fills up.
3. Say what the model reads on every turn and what tool calling does (the message roles move to the handout).
4. Use AGENTS.md to give the agent standing instructions.
5. Choose a fast or a smart model for a given task.
6. Commit, push and pull with GitHub through the agent.
7. Drive the **Interview → Plan (Approve / Edit / Reject) → Execute → Test / Debug → Iterate** loop to build a dashboard and a chatbot: let the agent ask questions first, get a written spec (`docs/spec.md`) and read and correct it, get a plan in opencode's Plan mode, then approve, edit or reject it before any code is written.

**S2**
1. Describe a table, a column and a row, and read their own database.
2. Have the agent store yfinance price history and build a watchlist that reads from it.
3. Write a system prompt and explain how it shapes the chatbot.
4. Build a Wiki from official sources they found, and show the chatbot's answers before and after.

**S3**
1. Tell a prompt, a skill and a multi-step workflow apart.
2. Generate a stock report from app data and check its numbers and claims.
3. Turn the report into a PowerPoint and improve it with structured feedback.
4. Recognise when to save a process as a workflow, and watch one run on another stock.

## 4. Goals, non-goals, anti-goals

**Goals**
- Hands-on work takes most of each session.
- We run every hands-on prompt in opencode before it goes on a slide.
- After every hands-on block there is a checkpoint, so anyone can switch to it and carry on.
- Session outputs match the curriculum (§7).

**Non-goals**
- Reading or writing code line by line.
- Days 4–5 material. Day 3 choices must still not block those days.
- Investment advice. The app analyses data; it never tells anyone to buy or sell.

**Anti-goals: these count as failures even if the app works**
- Someone falls behind in S1 and only watches for S2 and S3.
- Slides show prompts or screens that don't match what opencode really does.
- A session turns into a lecture.
- Made-up numbers or regulatory claims are presented as real.

## 5. Approaches considered

| | Approach | Trade-off |
|-|----------|-----------|
| A | Decks only, prompts written but untested | Fastest. One broken build can strand a participant for the rest of the day |
| **B** | **Decks + tested reference app with checkpoints + handouts** | **The most work. Every prompt is proven and nobody gets stuck** |
| C | Decks + handouts | Easier to follow than A, but the prompts are still untested |

**Picked: B** *(user)*. Hands-on is most of the time and S2 and S3 depend on S1's app, so recovery points are worth the extra build work.

## 7. Session design

The slide-by-slide headlines are in `docs/outlines/day3-outline.md` (S1 has 55 slides, S2 33, S3 29). Every session follows the same loop: **explain → hands-on → check → Q&A**.

**Skills** *(user)*: no skill kit is installed for participants. They use whatever skills their opencode setup already has. Every hands-on prompt must therefore work with **no extra skills installed**; that is the baseline we test against. S1 still focuses on skills: what a skill is, how to see which ones you have, and how a skill changes the result.

**Build method** *(user)*: every feature, in every session, is built with the same steps: **Brainstorm → Spec → Plan → Execute → Test → Iterate**. S1 teaches the steps in full. S2 and S3 reuse them for each new feature, starting from an update to `docs/spec.md`. S3 saves the steps as a reusable workflow. From S1 v3 on, the decks name the steps Interview → Plan → Execute → Test / Debug → Iterate.

## 8. Reference app

### 8.1 Stack
- **Frontend:** React + Vite *(user: React; call: Vite)*. Charts use a light chart library chosen by the builder.
- **Backend:** FastAPI *(user)*, Python. It runs yfinance, owns the database, keeps the LLM key and calls the LLM.
- **Database:** SQLite, as a single file *(call)*. It's easy to open and inspect in class, and Day 5 can swap it out if needed.
- **LLM:** the OpenAI-compatible API, configured in `backend/.env` as `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`.
- **Market data:** yfinance with tickers `NISP.JK`, `BBRI.JK`, `TLKM.JK`.

The hands-on prompts name this stack, so every participant's app ends up shaped like the checkpoints. That's what makes switching to a checkpoint safe.

### 8.2 Layout
```
financial-app/
  AGENTS.md            # project rules for opencode (created in S1 via /init)
  docs/spec.md         # what to build and why; updated for every feature
  docs/plan.md         # approved step-by-step plan for the current feature
  frontend/            # React + Vite
  backend/
    main.py            # FastAPI
    .env.example
    data/app.db        # SQLite (S2+)
    data/cache/        # cached yfinance responses (fallback)
  wiki/                # Markdown knowledge pages (S2)
  reports/             # generated reports and decks (S3)
  .opencode/           # saved workflow / command (S3)
```

### 8.3 Behaviour by checkpoint

| Tag | What exists | Acceptance check |
|-----|-------------|------------------|
| `s1-start` | Empty project with AGENTS.md, pushed to GitHub | Repo is visible on GitHub |
| `s1-spec` | `docs/spec.md` (dashboard: goals, out of scope, acceptance checks) and `docs/plan.md` (approved plan) | Spec has goals, non-goals and checks; plan has numbered steps |
| `s1-dashboard` | React page with the NISP latest price, change and a 1-year price chart; FastAPI serves the data live from yfinance | Page loads in the browser with real NISP numbers |
| `s1-chatbot` | Chat panel; the frontend sends the **whole message list** each turn; the backend forwards it to the LLM | Asking "what is NISP's latest price?" and then "and a month ago?" gets correct answers |
| `s2-database` | SQLite tables `stocks` and `prices`; a refresh action fills `prices` from yfinance | The agent can list the row count and the latest row for NISP |
| `s2-watchlist` | Watchlist page: add or remove a ticker; the dashboard reads from the DB, not live | Adding TLKM shows it with history; removing it hides it; dashboard shows one card per watchlist stock |
| `s2-wiki` | `wiki/*.md`, each page with its source URL; a system prompt sets the role, the rules (cite a source, no investment advice) and Wiki use | The 3 baseline questions get better answers, with sources |
| `s3-report` | `reports/NISP-report.html` with summary table, price chart, key stats and insight; every number traceable to the DB | Every number matches the dashboard |
| `s3-pptx` | `reports/NISP-deck.pptx`, plus the before/after-iteration versions | Opens in PowerPoint and Google Slides |
| `s3-workflow` | Trainer-only demo, built in `/data/training/deck`, not a participant checkpoint. A saved opencode command that produces the report and the deck for any ticker | Running it on TLKM produces both files |

### 8.4 Data model (S2) *(call)*
- `stocks(ticker PK, name, added_at)`: the watchlist.
- `prices(ticker, date, open, high, low, close, volume, PK(ticker, date))`: daily history.

### 8.5 Chatbot
- At S1 it can answer price questions because the backend adds the current NISP data to the context. This **teaches context, not tool calling**, which keeps the code small *(call)*.
- At S2 it adds a system prompt and Wiki pages. Before the Wiki gets too big for the context it moves to keyword retrieval. There's no vector database on Day 3 *(call)*.
- Its rules are: cite the Wiki page or data used, and say so when it doesn't know. When someone asks what to buy or sell, it refuses and gives the risks and facts instead.

### 8.6 Checkpoints and recovery
- The reference app is its own git repo with one tag per checkpoint. Each tag is also published as a downloadable zip.
- A participant recovers by asking the facilitator, who moves them to the checkpoint.
- Every checkpoint ships `data/cache/` so the app works even when Yahoo blocks or rate-limits requests.
- **Where it's hosted is open (§12).**

### 8.7 Forward fit (Days 4–5)
- Day 4 S1 looks at the FastAPI back end participants already have, adds endpoints for other apps and tours Swagger `/docs`.
- Day 4 S2 adds scraped news to the DB and the chatbot.
- Day 4 S3 puts login and roles in front of both React and FastAPI.
- Day 5 packages React + FastAPI + DB in Docker Compose.

## 9. Decks

- Single self-contained HTML files. `presentation-creator` writes the story and `frontend-slides` builds them, in "Low density / speaker-led" mode *(project rules)*.
- They use the house rules from `AGENTS.md`: assertion titles, ≤40 visible words per slide or per reveal step, and ≤60 on hands-on and instruction slides. Exceptions are prompts, code, quiz choices and essential reference tables.
- Every slide has one of these types:
  - **Talk:** a statement, then one diagram or example.
  - **Hands-on:** the goal, the exact prompt in a copy box, what you should see, the time-box and a "stuck?" line pointing to a checkpoint.
  - **Check:** a question, choices revealed on click, then the answer.
  - **Q&A** and **break** slides, with a timer.
- Speaker notes carry the narration, timing and common problems.
- The S1 Git segment reuses and restyles `demos/git-basics.html`, with GitHub added.
- The visual style is picked from `frontend-slides` style previews, once, and used for all three decks.
- **The headlines in `docs/outlines/day3-outline.md` must be approved before any deck is built (story gate).**

## 10. Handouts and facilitator guide

- **Handout (per session):** every prompt, ready to copy; what the result should look like; checks; and what to do if you're stuck (the checkpoint and the recovery sentence). One page per hands-on block.
- **Facilitator guide:** the pre-session checklist (API key works, Yahoo reachable, GitHub signup OK), the timing sheet, the known failures and their fixes, and which checkpoint to send people to.

## 11. How it gets built and verified

1. **Environment:** install opencode here, connected to the same kind of model access participants have.
2. **Prove the prompts:** from an empty folder, run each session's prompts in opencode exactly as a participant would. Rework a prompt until it works **3 times in a row from a clean start**. Tag each checkpoint after its acceptance check passes.
3. **Cross-platform:** check the commands and paths a participant sees on Windows and on macOS. If we have only one OS, the other is marked *(verify)* in the report.
4. **Decks:** story gate → style preview → build → check every slide's word count and click through it in a browser.
5. **Handouts and guide:** written from the tested prompts.
6. **Dry run:** a clean pass through all of Day 3 from `s1-start`, timed against §7.

**Done means:** all 10 checkpoints pass their acceptance check, every prompt on a slide matches the handout and the tested version, the decks pass the word budgets, and the dry run fits each session within 180 minutes.

## 12. Risks

| Risk | Mitigation |
|------|------------|
| Yahoo blocks or rate-limits a room of 30 people | Cached data in every checkpoint; the facilitator guide covers switching to cache |
| Participants have different skills installed, so results vary | Prompts tested with no extra skills; prompts name the stack and structure; checkpoints realign people |
| Two participants' agents build differently shaped apps | Prompts name the stack and structure; checkpoints realign people |
| Brainstorms differ person to person, so specs diverge | The brainstorm prompt fixes the scope (NISP dashboard: price, change, chart); the reference `s1-spec` shows a good result; small differences are fine |
| Brainstorm runs long (agent keeps asking) | The prompt caps it at about 5 questions; the facilitator calls time at 10 minutes |
| Web search turns up unofficial or wrong regulation pages | The deck teaches the official-source check; the checkpoint has a vetted Wiki |
| GitHub signup is slow (email verification) | Do it before the break; the facilitator guide covers fallbacks |
| LLM API quota during class | Pre-session check; use fast models for routine steps |
| opencode version differences (commands, `/init`, command folder) | Pin the version in the facilitator guide *(verify)* |
