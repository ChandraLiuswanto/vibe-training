A problem everyone has seen

Why names matter.

3 min. Start with a story. The shared watchlist is used by the whole team. One morning TLKM is gone. Who removed it? Today nobody can tell, because the app does not know who anyone is. Ask the room if they have seen this with a shared spreadsheet. By the end of today, the app will answer that question in one look.
03 / 16
Who are you? What may you do?

Two questions at the door.

4 min. Think of a hotel. At the front desk they check your ID once: who are you? Then you get a key card, and every door checks it: may you go in here? Your room opens; the staff room does not. Apps work the same way. Sign-in answers the first question. Roles answer the second, and they are checked every single time, not only at the start.
04 / 16
The company directory

Companies keep one list of staff.

4 min. Big companies keep one central list of staff and passwords. IT people may call it LDAP or Active Directory. Email, the HR portal and many other systems all ask that same list to check a password, so staff have one login for everything. Later, a real Financial App could ask the company list too. But that is a job for the IT team, not for today.

Practice directory · Practice names only

Today we practise with a pretend list.

4 min. Today the app checks a small pretend list with three practice people: Alya, Budi and Citra. It behaves like the real company list but never touches it, and nobody uses a real work password. The agent puts the check in one place, so later the pretend list can be swapped for the real one without rebuilding the app. Download the list during the practice hour.
06 / 16
Staying signed in

Sign in once. Carry a pass.

4 min. Nobody wants to type a password on every click. So after one successful sign-in, the app hands the browser a pass, like a wristband at an event. Every page shows the pass instead of the password. The pass expires after a while, and signing out cancels it. The pass is kept where page scripts cannot read it, and it is never written down in logs.
07 / 16
Who can do what

Two roles: User and Admin.

4 min. Two roles keep it simple. Users, Budi and Citra, get the everyday app: dashboard, Wiki, chatbot and the shared watchlist. The Admin, Alya, gets all of that plus two extra things: managing people and their roles, and reading the activity history. Roles are kept inside the app, not in the company list. Being in the company list only proves who you are.
08 / 16
Quick check

Is hiding the button enough?

3 min. Quiz the room. Budi does not see the Admin button, because the screen hides it for Users. Is the admin page safe? Pause for answers. No: Budi can still type the address, or a tool can send the request directly. Hiding a button is tidy, but it is not a lock. The lock has to be on the server. Click an answer to reveal the feedback.
09 / 16
Same request, two answers

The server decides, every time.

4 min. Here is the lock. Budi and Alya send the very same request: show me the users list. The server checks who is asking and their current role. Budi gets a polite refusal. Alya gets the list. If Alya later changes Budi's role, the change applies on his very next click, even if he stayed signed in. In the prompt this is Stage 3.

11 / 16
Who did what, and when

The activity history.

5 min. Back to our story. The history now answers it: at 09:05 Budi removed TLKM. Each line shows the time, the person, the action and the result, including attempts that were blocked. The history can only be added to. Nobody can edit or delete a line, not even the Admin, so people can trust it. The times shown are examples.
12 / 16
What goes in the history

Record actions, never secrets.

3 min. A history is only useful if it is safe to read. Record sign-ins and sign-outs, watchlist changes, role changes and blocked attempts. Never record passwords, the sign-in pass or secret keys. Even with that rule, only the Admin can read the history.

# Session 3 · Who can do what: sign-in, roles, admin page and history

60-minute presentation, then 60-minute practice.
Training only: a practice directory on your own laptop; no LDAP protocol or company connection.
Practice people: alya (Admin), budi and citra (Users).

## Before you paste the prompt

1. Open your existing Financial App from Sessions 1 and 2 in your coding agent. Keep it on your own laptop (loopback only).
2. Download mock-directory.json from the deck and place it in your project root. It has names only: no passwords, roles or grants.
3. Paste the one prompt below. The agent works in five stages and stops at each STOP. Read what it did, then reply "yes" to continue.
4. Never paste a password into the agent chat.
5. Use two separate private browser windows to test different people.

Practice: 00–15 plan + sign-in; 15–30 roles; 30–45 admin page; 45–55 history; 55–60 prove it with two windows.
The prompt needs rehearsal against your actual app. If a check is blocked, record it as unfinished, not passed. Ask a facilitator for help or extra time; never remove safety checks.

Session 3 · Add sign-in, roles, an admin page and history (one prompt, five stages)

Work inside my existing React/FastAPI Financial App from Sessions 1 and 2. Preserve any existing news feature and its manual refresh rules. Reuse its front end, back end, SQLite database and project conventions. Inspect the project instructions, spec, auth (if any), API routes, storage, startup commands and tests first. This is a local training build with a mock directory: no LDAP protocol, no real LDAP server and no corporate directory connection. It is not production security.

Work through the five stages below in order. At every line marked STOP, show me what you found or propose, then wait until I reply "yes" before continuing. If I say anything other than yes, stay in that stage.

RULES FOR EVERY STAGE
- Preserve the dashboard, prices, Wiki, chatbot, shared watchlist and Session 1 IDR/USD feature where present. Nothing is rebuilt from scratch.
- Prefer installed packages and the Python standard library. Explain any new package and STOP for approval before installing it.
- Never store or log a plain password, cookie, token or session ID. Never store passwords or tokens in browser localStorage. Never ask me to paste a password into chat.
- Apply every permission check in FastAPI, not only in React. Hiding a menu is not protection.
- Keep the app bound to loopback (127.0.0.1). Do not weaken a protection to make a test pass.
- Report each check as PASS, FAIL, BLOCKED or NOT RUN with real evidence; never claim an unrun check passed. If something fails, explain the cause in plain language and propose a bounded fix before changing anything.
- Do not commit or push.

STAGE 1 · INSPECT AND PLAN (no code yet)
Use mock-directory.json from the deck download. If it is missing, stop and ask me to download it; do not invent a different roster. It lists three practice identities, alya, budi and citra, with no passwords, roles or grants. Directory authentication (who are you?) stays separate from app roles (what may you do?), which live in the app database keyed by username.
Ask at most three essential questions, one at a time. Then update docs/spec.md and propose a numbered plan in four build stages: sign-in, roles, admin page, history. For each stage list planned files, risks and tests in plain language. Include a permission matrix, the session/CSRF design and how two Admins changing roles at once can never remove the last active admin. Flag missing dependencies and time risks.
STOP: wait for my approval of the plan.

STAGE 2 · SIGN-IN WITH THE MOCK DIRECTORY
Put the mock directory behind one back-end function that checks a username and password, with a comment marking where a real directory call would go later. Seed alya, budi and citra with the shared class practice password Training-2026, stored only as a salted hash from a slow standard-library function (scrypt or PBKDF2). This password is for this local exercise only and must be replaced before any public deployment.
Add a sign-in page and sign-out. Use the same generic message for an unknown user and a wrong password. Use opaque server-side sessions with a random ID in an HttpOnly, SameSite=Lax cookie, a defined expiry, sign-out invalidation and CSRF protection for state changes including sign-in. Every existing API except sign-in returns 401 without a valid session.
Add and run tests for successful sign-in, both failure cases, missing/invalid sessions, CSRF refusal and sign-out. Tell me how to check them in the browser.
STOP: show changed files and test results, and wait for approval.

STAGE 3 · ADMIN AND USER ROLES
Store a role per user in the app database. Default to User and seed alya as Admin; budi and citra are Users. Never ask the directory for roles.
Use one shared back-end role check for every admin-only endpoint: not signed in returns 401, a signed-in User returns 403, an Admin succeeds. Re-check the current role on every protected request so a promotion or demotion takes effect on the next request, even in an existing session.
Users and Admins can use the dashboard, prices, Wiki and chatbot and change the shared watchlist. Only Admins can list users, change roles or read the history. Show the current name and role in the header; hide the Admin menu for Users, but explain that the back-end check is the real protection.
Add and run tests proving the 401, 403 and success outcomes.
STOP: show changed files and test results, and wait for approval.

STAGE 4 · ADMIN PAGE
Add Admin-only endpoints to list users and change a role, reusing the shared check. Build an Admin page showing the number of users, each name and role, and Promote/Demote buttons. alya, budi and citra are listed from the start.
Refuse to demote or remove the last active admin, including through a direct API request and when two changes arrive at once; explain the refusal on the page rather than relying on a disabled button.
Add and run tests for listing, promoting, demoting, last-admin refusal and User refusal.
STOP: show changed files and test results, and wait for approval.

STAGE 5 · ACTIVITY HISTORY (AUDIT TRAIL)
Add one add-only audit table with time, user, action, target and result. Record sign-in success and failure, sign-out, watchlist add/remove, role changes and refused (403) requests. Never record passwords, cookies, request bodies, tokens or session IDs; explain how unknown-user sign-in failures are recorded safely. Provide no edit or delete endpoint. Reading the history is Admin-only via the shared check, without logging recursively.
Add an Admin-page section with the latest 50 records, sign-ins today and the number of users, derived from the same records.
Add and run tests for each event type, Admin access, User refusal and the absence of sensitive fields.
STOP: show changed files and test results, and wait for approval.

FINAL CHECK WITH TWO BROWSER WINDOWS
Use two separate private windows. Then run and report:
1. A wrong password is refused. budi signs in and changes the shared watchlist.
2. budi gets 403 from both the users and history endpoints by direct request, not just a missing menu.
3. alya signs in. As the last active admin she cannot demote herself; then she promotes citra, and citra's new role applies on her next request.
4. As Admin, read the history and confirm each step shows the right user, action, target and result, with no secrets in your evidence.
5. List the checks I must still do by hand in the browser (header identity, menu differences, role change).
Finish with changed files, real test results, remaining risks and manual checks in plain language. Do not commit or push.
